Distributed Compute Node

FlexNode

A distributed compute node for mobile robots — high-current field-oriented motor control and sensor fusion, all over CAN-FD. One node per actuator, daisy-chained back to an onboard Jetson, so every joint gets local hard-real-time control while the host just plans. The goal: any sensor-fused robot reduces to buy FlexNodes + actuators + sensors, wire power and CAN — no electronics development.

What it is

FlexNode fuses a field-oriented motor controller and a sensor-fusion front end onto a single compact PCB that hangs off a CAN-FD bus. Many nodes daisy-chain back to a host, so each limb or joint runs its own tens-of-kHz current loop locally while the host does high-level planning.

It began as a fork of the mjbots moteus r4.11 controller — the proven power stage, gate driver and STM32G4 core are kept intact — and adds the digital sensing and I/O a distributed robot node needs: a 6-axis IMU, optional multizone ranging, a servo/aux port with onboard current sensing, addressable status RGB, and everything reported over CAN-FD.

Crucially, the fleet runs one firmware image: node identity — CAN id, encoder sources, which peripherals are attached — is per-node configuration, not code. Ten BLDC actuators means ten identical boards (twelve ordered, for attrition), two wires between them, and a config file each.

The design target is CatBot, a lightweight, highly agile jumping quadruped: FlexNode drives its geared hip actuators and lighter leg motors, one node per actuator, all chained to the onboard Jetson.

Milestone · 6 September 2026

First boot

First light: FlexNode booted and talking over SWD, its onboard status LED driven by the board’s own firmware, wired to an ST-Link programmer — 6 September 2026.

A v1.0 board came up on a 13 V bench adapter — no motor and no encoder fitted, the AS5047 not yet soldered. The 5 V buck and the 3.3 V logic rail both measured stable — the whole point of a first power-on: prove the power tree before anything downstream gets a vote. (Boards were X-ray inspected before assembly. Two days later a current-limited supply did spin a motor — first spin.)

Debug went in over the SWD header with an ST-Link V2 (xPack OpenOCD on Windows, the probe bound to WinUSB with Zadig). The first session was deliberately read-only — identify the die and touch nothing. It answered STM32G47x, IDCODE 0x20036469, 512 KiB dual-bank, factory option bytes, flash blank: exactly the part the design assumes.

Then one option byte changed. nSWBOOT0 was cleared so the chip boots from flash rather than the ROM bootloader — on FlexNode PB8 doubles as BOOT0 and is held high by the I²C pull-up, so left alone the board would wake up in the bootloader forever.

First light came from a 948-byte bare-metal program — GPIO and SysTick, nothing else — fading the onboard WS2812B on PF0 from warm white to blue. First try. A small thing that proves a lot at once: clock tree, code executing from flash, GPIO, and the LED net.

Then the real image — the moteus → FlexNode port — was flashed, and it runs: a steady soft-blue status LED, servo reporting stopped mode.

Later the same day the LSM6DS3TR-C IMU answered over I²C and streamed samples — verified with the board in hand by a tilt-to-hue demo on the status LED, no CAN adapter needed.

New in that image: the status & lighting driver (fw/ws2812_led.{h,cc}). Pixel 0 is the node's own status LED and blinks fault codes — tens digit in amber, units in red — while pixels 1..N on the same data line are master-control RGB lighting for whatever the robot needs lit. PF0 has no usable SPI or timer output on the G4, so the stream is bit-banged from the main loop against the DWT cycle counter, with interrupts masked only during each bit's high pulse (under a microsecond) — the 30 kHz FOC interrupt never waits on an LED. Behaviour is configuration, not code: led.count, led.brightness, led.master_r/g/b, led.fault_override.

Milestone · 8 September 2026

First spin

Two days after first boot the power stage was energized for the first time and a GIM 8108-8 turned under FlexNode's own drive. Deliberately the least ambitious way to do it: open-loop voltage FOC — a commanded electrical angle and voltage through the stock moteus controller, no encoder in the loop — from a 13 V bench adapter that current-limits at ~1 A, so the supply, not the winding, was the thing that could give out. The test image is a throwaway on its own branch; the FOC, PWM, current-sense and gate-driver code underneath it is untouched moteus.

It was staged. Each run is a fixed loop — align, a forward half-sine speed profile, a square reverse, rest — with the drive voltage stepped up between stages and a wall of software aborts around it: bus sag, overcurrent, FET temperature, any moteus fault, a mode watchdog, and a hard cap on cumulative energized time. The stage that mattered ran eight loops, ~140 s energized, zero faults, the FETs plateauing at 38.7 °C from ~32 °C idle. Then a deliberate over-demand: the next stage asked for more than the adapter could give, the bus collapsed from 12.6 V to 10.5 V, and the bus-sag abort caught it and de-energized cleanly — a protection path exercised for real, not just written.

The sensing came out of it validated too. The DRV8353S came up and its three current-sense channels calibrated; phase currents track the V–I model to a few percent and sum to ~zero, which checks the sense chain and the phase wiring together. Bus-voltage telemetry was checked against a DMM — 12.82 V on the meter vs 12.50 V on the board — closing the loop on the as-built 1.2 kΩ divider: the firmware compensation was right to ~2.5 %, and is now trimmed. And a sensorless extra: every loop opens with a V–I sweep that fits the phase resistance on the board (0.33–0.44 Ω); copper's 0.393 %/K turns any drift into a winding-temperature estimate the unpopulated motor-NTC pad cannot provide.

How it fits

Each actuator carries its own FlexNode bolted to the back of the motor — closing the FOC loop millimetres from the windings and the magnetic encoder, with only a CAN-FD pair and power leaving the joint. Split the chain left/right (or front/back) and a single bus fault takes down one side, not the whole robot.

Powering it safely

Bus voltage: up to ~44 V (10S LiPo). Bus ceramics are rated 50 V and the power FETs 60 V — sized for that rail, with no margin to spare above it.

⚠ Never hot-plug a FlexNode onto a live pack. Cable inductance and the ceramic bus form an LC tank that can ring toward 2× and blow past the 60 V FETs. Always bring the bus up through the core board's pre-charge — or a current-limited supply on the bench.

Firmware note: the motor phase A/C outputs are swapped in copper relative to stock moteus. The FlexNode firmware compensates with a drive-side channel remap — verified pin-by-pin against both schematics and already implemented in main; hardware confirmation waits on the encoder, since open-loop drive is indifferent to it. Do not flash unmodified moteus — it would close the current loop on the wrong winding.

Firmware & flashing

The firmware is a fork of moteus, keeping the FOC inner loop, FDCAN protocol and bootloader byte-for-byte. The compatibility layer is implemented and builds green: board ID hardcoded to {family 0, hw_version 8} with the strap-pin autodetection deleted outright, the AS5047 chip-select moved to PC6, and the phase-order fix — a two-line drive-side pin remap, netlist-verified, that re-pairs drive and sense without touching a single line of control code (hardware confirmation waits on the encoder; open-loop drive can't tell). Since first boot it also carries the WS2812B status/lighting driver on PF0, the LSM6DS3TR-C IMU as an aux-I²C device, and the FlexNode register-block skeleton. Application image ≈ 428 KiB with ~16 KiB free — and the flash budget is now measured rather than feared: newlib-nano, an exception-stub TU and -Os on the controller TU return ~84 KB in real builds without touching the drive path (flash-budget.md).

Flash over the FLASH header (SWD — NRST · CLK · DIO · 3V3 · GND), or via the moteus bootloader over CAN.

1 · Build — in WSL (Ubuntu 22.04):

  1. Clone the repo, then build the target image:
    cd moteus-r4-parent && tools/bazel build --config=target //:target
  2. The FlexNode deltas — hw_version 8, the CS remap, and the phase-order fix — are in main; building from it carries them automatically.

2 · First flash — virgin board, over SWD: connect an ST-Link / J-Link to the FLASH header (NRST · CLK · DIO · 3V3 · GND) and write the combined bootloader + application image to 0x08000000 with STM32CubeProgrammer or OpenOCD.

3 · Updates — over CAN, once the bootloader is on: with an fdcanusb or pi3hat on the bus,
python3 -m moteus.moteus_tool -t <id> --flash <firmware.elf>

4 · Calibrate — python3 -m moteus.moteus_tool -t <id> --calibrate — first spin on a current-limited supply, and confirm calibration converges before allowing full current.

Boot, flash, the status LED, the IMU, bus and current sensing and open-loop drive are hardware-validated; closed-loop control and CAN are not — and stock moteus binaries will not run correctly on this board (repurposed strap pins, swapped phases). The living reference is docs/firmware.md.

The distributed CAN layer

FlexNode extends the moteus CAN-FD register protocol instead of inventing a new one. The v2 design models a node as one axis plus typed channel slots — sixteen strided register blocks from 0x200 whose type the host reads at boot, so adding a peripheral kind adds an enum value, not a register range, and one host driver covers every node. A small fixed block at 0x080 carries capabilities, profile id and fleet state, and a node's identity is a name in config (0x0C0), not a bus address. Each frame is still composed per node: the host queries only the hardware a node actually carries.

Two more decisions came from CatBot's realities. Build-time profiles: hardware cannot change at runtime, so a reflash on a hardware change is acceptable and channel drivers compile in or out — the release valve for the flash budget, without changing what any register means. And graded host-loss autonomy: if the host goes silent, nodes step through warning → timed-out → deputy-commanded states over the 0x7f broadcast every node already accepts. Traffic stays strictly poll-response on a two-lane schedule — loop-critical signals every cycle, one node's full sensor block per cycle on a rotating slow lane. The 8 Sep 2026 CatBot subsystem design puts ten FlexNodes on one ~45 cm chain behind an STM32G4 corenode as bus master: ~1.95 ms per full cycle, ~350 Hz usable at two-thirds bus occupancy.

None of it has been exercised over a real bus yet — there is no CAN-FD adapter on the bench, and the register block has never been read. The full spec — channel model, register map, profiles, host-loss states, bus-budget math — is in docs/can-layer.md.

Engineering emphasis

CAN-FD as the spine

Every node hangs off one differential pair; the fast data phase carries both commands and telemetry. Nodes daisy-chain, with termination only on the leaves — wiring a limb is two wires plus power.

One node per actuator

The current loop closes millimetres from the windings, not across the robot. The Jetson only plans; each joint owns its own hard-real-time control. Splitting the bus per side buys fault isolation for free.

Verified before fabricated

The power stage, current limits and every BOM part number were independently checked against datasheets before committing copper — inductor sizing vs. the buck's current limit, cap voltage ratings, footprint/pinout matches, all 37 line items.

A two-line topology fix

The board's A/C phase swap is corrected in the firmware's pin table, not its control code — the PWM channel mapping follows the pins generically, so the entire FOC core stays byte-for-byte stock and calibration semantics survive. Verified against both netlists first; hardware confirmation waits on the encoder.

One image, N configs

Node identity lives in persistent config, not code. The whole fleet flashes the same binary over CAN; a config file makes a hip a hip and a knee a knee. No per-node builds, ever.

Flash spent where it counts

The ToF sensor needs an ~84 KB init blob the MCU can't spare — so the host streams it over the CAN diagnostic tunnel at boot. Zero flash cost; foot-contact detection is thresholded on-node instead, so the loop-critical signal is a single byte.
